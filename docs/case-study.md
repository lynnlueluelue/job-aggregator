# 项目案例页 · 考编公告聚合站（Job Aggregator）

> 一句话定位：**一个人靠 AI 从 0 到 1 独立完成的"个人求职 Agent"** —— 自动抓取多个官方渠道的招聘公告，按用户画像自动核对"我能不能投"，从"海量信息"到"只看我能上的岗位"。

> 说明：本文是面向展示/简历的案例通稿。文中所有个人画像与地区均已泛化（示例：{地区} / {用户画像}），实际使用请替换为你自己的信息，且不编造数据。

---

## 一、项目背景与问题

体制内求职的核心痛点不是"信息少"，而是**信息过载 + 筛选靠肉眼**：

- 每天要刷十几个政府/国企官网、公众号、招聘平台；
- 每条公告要人工核对 4 个硬条件：**年龄、党员、专业、招聘对象**；
- 附件里的岗位表（xlsx/docx/pdf）才是专业要求的真正出处，光看标题必漏。

市场上的聚合工具（如"公考雷达"）要么收费、要么不贴合个人画像。**所以自己建一个。**

> 项目动机足够真实：它不是一个 demo，而是求职期间每天高频使用的工具。能解决自己真实问题的产品，才会认真打磨。

## 二、做了什么（产品 → 技术 → 设计）

### 1. 产品：先梳理"筛选逻辑"，再写代码

开发前先跟 AI 反复对齐**筛选逻辑**，期间明确喊停 3 次"先不要做"：

- 从"收集所有招聘信息" → 收敛为**唯一目标**："找到适合我的 + 我可以投递/参加考试的岗位"；
- 建立 `USER_PROFILE`（年龄 / 学历 / 政治面貌 / 专业 / 目标单位）作为**所有筛选规则的输入**；
- 规则逐条拆解：中小学教师岗排除但高校行政岗保留（看招聘单位性质，不搞一刀切）、年龄按学历档口径提取上限、专业分"对口/相关/不符/未标注"四态、附件岗位表解析不出标"未解析"**不误杀**。

> 这一段教会我的：**产品不是功能的堆叠，是"先定义问题边界，再做减法"**。AI 会默认给你一堆功能，真正有价值的是想清楚"哪些不做什么"。

### 2. 技术：Python + Flask + 原生 JS 全栈闭环

| 模块 | 实现 |
|---|---|
| 抓取层 | requests + BeautifulSoup，覆盖多个渠道（静态 li 页 / 详情页 / **JSON API** 三类反爬形态） |
| 判定层 | `content_judge` 招聘信号分 − 噪音分×1.5 → 公告/岗位/公示三分类 |
| 核对层 | `screen_item` 按用户画像逐条硬核对，产出 `ok / reasons`，不符进 `blocked` |
| 附件层 | zipfile 免依赖解析 xlsx/docx + pdfplumber 解析 pdf，补查岗位表专业要求 |
| 去重层 | 标题+日期 MD5 指纹 + 跨渠道同源识别，保留官方渠道高得分者 |
| 前端 | **单文件 index.html（原生 JS，零框架）**，含筛选/标记/追踪/搜索 FAB/骨架屏 |
| 通知 | 每 3 小时自动刷新，**仅第一梯队新公告弹桌面通知** |

**遇到并解决的硬问题**：本地站反爬限流（加延迟+标题特征过滤）、平台详情页需登录（退化为标题+学历核对）、个别官网 SSL 不通（转书签常驻入口）、UTF-8 中文乱码（环境变量兜底）。

## 三、三个亮点

### 亮点一：筛选逻辑的产品化 —— "不能投的岗位根本不该出现"

市面上聚合站把信息搬过来就完事，这里做成**决策引擎**：

```
渠道列表 → 内容判定(岗位/公告/公示) → 报考条件核对(年龄/党员/专业/择业期)
        → 附件岗位表兜底 → 硬排除 → 去重排序 → 前端渲染
```

用户最终看到的是**已经过滤掉大量噪音**、且每条都标了"为什么我能投/不能投"的清单。排除项半透明但可展开查看原因（`显示已排除`），**宁可标"未解析"也不误杀** —— 这是对用户负责的信息策略。

**专业/学历判定的"结构化信号"升级**：标题和正文是弱信号，光靠它们"博士岗"会误杀有可投岗的公告、"专业"判定会漏。后来发现高校人才网的**职位列表页**把每行职位的**学历**和**需求专业**都结构化列出来了（比正文精准得多），于是增加一层判定：职位列表含用户可投档 → 解除标题"博士"误排；需求专业命中对口/相关词 → 直接定级；无关专业为主 → 定"专业不符"。这层信号让误杀率明显下降，还顺带清掉了正文层相互矛盾的判定。

### 亮点二：免费替代付费 —— "公考雷达"的私有版

商业工具的核心能力（多源聚合、岗位筛选、追踪提醒）用**本地离线运行 + 每 3 小时刷新 + 桌面通知**全部免费实现，还多了商业工具没有的：**跨渠道去重、自定义追踪指定考试的结果公示、按用户画像自动核对**。数据 100% 本地，不产生任何云端依赖。

### 亮点三（重点）：UI 优化 SOP —— 从"调了 11 轮颜色还不满意"到"一套可复制的方法"

**失败经历（真实）**：作为设计小白，曾连续 11 轮只改 hex 色值，仍不满意。当时 AI 给了一句点醒的诊断：

> "你一直在改**症状**（单个颜色），而不是**系统**。每改一个 hex 只是让局部顺眼一点，但整体的层级、对比度、留白问题始终没解决。"

诊断挖出的真相：85 处硬编码颜色、54 个去重值散落各处；某梯队浅蓝底配白字对比度仅 1.43:1（不可读）；页面同时混着扁平+渐变+阴影三种设计语言。

**提炼出的七步 SOP（从此告别盲调色）**：

| 步骤 | 做法 | 解决的问题 |
|---|---|---|
| ① 先诊断后动手 | 设计系统生成器 + 代码审计：对比度计算表、硬编码色统计、结构问题清单 | "不知道问题在哪" |
| ② 定风格再调色 | 从风格库锁定适配方向（Flat / Swiss / Trust & Authority），不混搭 | "为什么总是差点意思" |
| ③ 先出静态稿再改码 | 独立 `preview.html` 并排渲染 2-3 种风格，满意才应用正式文件 | "看不到效果只能等成品" |
| ④ Token 化配色 | 所有颜色收敛到 `:root` 变量，一处改全局 | "改一处漏三处" |
| ⑤ 对比度把关 | 选色先算 WCAG 对比度，不靠肉眼 | "看着顺眼却看不清" |
| ⑥ 构件对照表 | ASCII 页面结构图 + CSS 类名映射，和 AI 沟通有共同语言 | "不知道构件叫什么" |
| ⑦ 原型图驱动精修 | 用原型工具出整站设计稿，截图对照微调，参考图 > 文字描述 | "改来改去都是猜" |

**最终交付**：统一 token、对比度达标的设计系统，并沉淀出 `component-map.md` 和 `ui-design.md` 两份可复用文档 —— **这套方法可以直接复用到下一个项目，不用再从零踩坑。**

## 四、结果与数据

- **多个自动抓取渠道**（地区事业单位、国企央企、高校）+ **多个书签常驻入口**；
- **每 3 小时自动刷新**，第一梯队新公告第一时间弹桌面通知；
- 筛选逻辑跑通真实数据：一段时间内公告经画像核对后，**只剩真正能投的目标岗位**（噪音信息基本排除）；
- **专业判定可解释**：样本岗位实测分布 对口 / 相关 / 不符 / 未标注，互斥标签无冲突；
- 单文件前端（无框架）+ 本地 Flask 服务，**开机自启、离线可用**；
- 沉淀文档：`architecture.md`（架构）、`ui-design.md`（设计系统）、`component-map.md`（沟通工具）。

## 五、带走的方法论

1. **做给自己用的产品，先想清楚问题边界** —— "找到我能投的岗位"，而不是"收集所有信息"；
2. **AI 是协作伙伴不是打字机** —— 会打断它说"先不要做，我们先把逻辑梳理清楚"；
3. **设计要系统化，不要玄学调参** —— token 化 + 对比度 + 静态稿先行，这套 SOP 可复制；
4. **文档是第二产品** —— 每一轮改动同步方案文档，让项目可交接、可迭代。
